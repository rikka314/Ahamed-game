>
> 建立日期：2026-08-24
>
> 适用阶段：游戏层与模型层独立并行开发，直至满足 MVP 合并门槛
>
> 相关文档：`技术栈.md` 是游戏层基线；`开源资源与技术方案.md` 是模型层基线；本文是两者之间唯一的共享边界基线

## 1. 文档目的

本项目在前期阶段拆成三个顶层边界：

```text
apps/game/
├─ game/      游戏层独立项目
├─ model/     模型层独立项目
├─ share/     共享连接层
└─ docx/baseknowledge/
   ├─ 技术栈.md
   ├─ 开源资源与技术方案.md
   └─ 共享层基本内容.md
```

游戏层和模型层分别独立开发、独立运行、独立测试。共享层负责固定双方必须一致理解的概念和接口，使两条开发线在没有直接依赖对方内部代码的情况下，仍能针对同一份契约完成端到端闭环。

当两边都达到本文定义的合并门槛后，再合并进入统一 MVP 开发。合并并不意味着删除边界；即使部署在同一进程中，游戏表现、医学模型和共享契约仍保持逻辑隔离。

本文主要解决：

1. 游戏层与模型层分别拥有什么状态和规则；
2. 双方使用哪些稳定 ID、DTO、Schema、API 和事件；
3. 隐藏病例、答案和评分规则如何不泄露到客户端；
4. 两边如何使用 mock、fixture 和契约测试独立开发；
5. 什么条件满足后才允许合并制作 MVP；
6. 尚未确定的设计在哪里留空、由谁审核和何时冻结。

## 2. 决策状态标记

本文使用三种状态，避免把建议误读成已经实现的事实。

| 标记 | 含义 | 变更要求 |
|---|---|---|
| 已决定 | 当前架构基线，双方实现必须遵守 | 修改前需要更新本文和变更记录 |
| 建议 | 当前推荐方案，实施前仍可调整 | 调整时记录理由及对双方的影响 |
| 待审核 | 信息不足或需要产品、医学、运营决定 | 保留空位，不由开发者擅自填充 |

当前已决定：

- 前期使用 `game/`、`model/`、`share/` 三个顶层边界；
- `game/` 与 `model/` 不直接依赖对方内部模块；
- 所有跨层通信必须遵守 `share/` 的版本化契约；
- 隐藏病例事实、答案、rubric、prompt 和模型密钥不得进入客户端；
- 检查结果来自通过双 AI 交叉验证的冻结病例包，不由在线 LLM 临场编造；
- 模型输出不能直接修改游戏货币、经验、库存、时间或解锁；
- 游戏层可以使用 mock 模型独立完成闭环；
- 模型层可以使用 headless client 独立完成闭环；
- 两边通过同一组 fixture 和 contract tests 后，才允许进入 MVP 合并阶段。

## 3. 三层职责总表

| 领域 | 游戏层 `game/` | 模型层 `model/` | 共享层 `share/` |
|---|---|---|---|
| 玩家移动 | 实现与持有状态 | 不参与 | 不定义逐帧协议 |
| 场景和地图 | 实现、加载、渲染 | 不参与 | 只允许共享稳定 `locationId` |
| NPC | 位置、外观、动画、普通行为 | 患者人格、病例回答 | `npcId`、`patientRoleId`、`caseSessionId` 绑定 |
| 问诊 UI | 输入框、历史展示、焦点、流式呈现 | 理解问题、披露事实、生成回答 | Turn 请求、事件和错误 Schema |
| 检查 | 设备、解锁、费用、动画、时间推进 | 医学可用性、固定结果、报告文本 | `deviceId` 与 `testId` 映射、请求和结果 DTO |
| 诊断 | 表单、确认流程、结果呈现 | 术语匹配、答案判定、医学评分 | Diagnosis 和 Evaluation DTO |
| 模拟经营 | 金钱、经验、声望、库存、升级 | 不决定经营状态 | 只提供稳定的医学评分输入 |
| 病例 | 只持有允许展示的投影 | 完整病例、答案和 rubric | CaseSummary 与 ClientCaseProjection Schema |
| 存档 | IndexedDB 本地游戏进度 | 服务端会话与医学轨迹 | 存档与会话关联字段、恢复语义 |
| 安全 | UI 提示、输入限制、隐私入口 | 医疗安全、注入防护、隐藏事实保护 | 数据分类、错误码、审计字段 |
| 测试 | 游戏单测、浏览器测试 | 模型评测、headless 测试 | 契约测试、兼容测试、fixture |
| 版本 | 游戏内容 build 和存档版本 | 病例、prompt、模型版本 | contract、schema、event 版本 |

## 4. 依赖与所有权原则

### 4.1 单向依赖

允许的依赖关系：

```text
game  ──依赖──> share <──依赖──  model
```

禁止：

```text
game  ────────> model 内部模块
model ────────> game 内部模块
share ────────> game 或 model 的具体实现
```

共享层必须保持实现中立。公共契约不能直接暴露 Phaser Scene、React Component、数据库 ORM entity、模型 SDK response 或某个供应商特有对象。

### 4.2 状态唯一所有者

每个状态只能有一个权威所有者：

| 状态 | 权威所有者 | 其他层可见形式 |
|---|---|---|
| 玩家位置、朝向、当前地图 | 游戏层 | 必要时只暴露稳定 location 信息 |
| 金钱、经验、声望、库存 | 游戏层 | 模型层不可见，除非未来有明确需求 |
| 病例完整事实 | 模型层 | 只输出允许披露的投影 |
| 已披露事实集合 | 模型层服务端 | 游戏层可收到本轮新增 ID，但不拥有完整真相 |
| 检查医学结果 | 模型层 | 游戏层收到完成后的展示投影 |
| 设备拥有和解锁 | 游戏层 | 模型层不决定 |
| 诊断医学评分 | 模型层 | 游戏层只消费结构化结果 |
| 评分到奖励的换算 | 游戏层 | 模型层不决定 |
| 会话阶段 | 模型服务端为医学权威；游戏层保存显示镜像 | 通过共享状态事件同步 |
| 契约版本 | 共享层 | 双方在构建和运行时声明支持范围 |

### 4.3 禁止隐式共享

- 不使用相同数据库表作为两边的隐式接口。
- 不通过读取对方日志文件推断业务状态。
- 不以显示名称作为稳定 ID。
- 不以数组下标、Tiled GID、Phaser 对象 ID 或数据库自增 ID 作为跨层长期标识。
- 不在 prompt 中藏只有游戏层才知道的经营规则。
- 不在游戏配置中复制病例答案或评分规则。

## 5. 前期独立开发模式

### 5.1 游戏层独立开发

游戏层通过 `share/mocks/` 提供的 mock adapter 模拟模型服务。mock 必须支持：

- 创建固定病例会话；
- 返回患者初始主诉；
- 对固定问题流式返回患者回答；
- 返回可用和不可用的检查结果；
- 接收正确、错误和重复诊断；
- 返回完整、部分和失败评分结果；
- 模拟延迟、超时、断流、重试和会话过期；
- 模拟病例版本不兼容；
- 模拟安全越界响应；
- 保证同一 fixture 的输出可复现。

游戏层独立验收不要求真实 LLM，但要求真实完成：

```text
世界交互 → DOM 问诊 → 检查 → 诊断 → 结果 → 经营奖励 → 存档恢复
```

### 5.2 模型层独立开发

模型层通过 `share/mocks/` 或 `share/fixtures/` 提供的 headless client 模拟玩家和游戏客户端。headless client 必须支持：

- 创建和恢复会话；
- 发送单问题、多问题、无关问题和恶意输入；
- 申请有效、无效、重复和未解锁检查；
- 提交诊断及鉴别诊断；
- 中断和恢复流式响应；
- 发送重复幂等请求；
- 验证响应 Schema、事实 ID、状态变化和错误码；
- 运行固定随机种子或固定模型输出的回归测试；
- 导出完整、可审计的事件轨迹。

模型层独立验收不要求 Phaser 或像素场景，但要求通过 API/headless runner 完成完整医学闭环。

### 5.3 共享 fixture 的地位

fixture 是双方共同使用的可公开测试数据，不得包含：

- 真实患者数据；
- 未获授权的病例文本；
- 真实 API key；
- 生产 prompt；
- 生产病例答案；
- 任何个人身份信息。

建议至少准备：

| Fixture | 用途 |
|---|---|
| `happy_path_case` | 标准问诊、检查、正确诊断 |
| `wrong_diagnosis_case` | 错误诊断和低分结果 |
| `unknown_fact_case` | 验证 unknown 不被回答为 absent |
| `duplicate_request_case` | 验证幂等和重复扣费保护 |
| `unsafe_input_case` | 真实病情、提示注入或索要答案 |
| `stream_interrupted_case` | 验证流式中断和恢复 |
| `expired_session_case` | 验证过期会话和本地存档处理 |
| `version_mismatch_case` | 验证契约或病例版本不兼容 |

Fixture 的具体病种和文本由模型层冻结；病例发布必须附带临床安全与诊断质量两个独立 AI 角色的交叉验证记录。

### 6.1 语言中立要求

即使游戏层使用 TypeScript、模型层未来使用 Python，共享规范也必须有语言中立表示：

- JSON Schema 作为线上的运行时数据合同；
- OpenAPI 或等价说明描述 HTTP 接口；
- AsyncAPI 或 Markdown 状态表描述流式事件；
- TypeScript 类型可以自动生成或手工维护，但不能成为唯一事实源；
- Python Pydantic model 可以从 Schema 映射，但不能定义额外、未公开字段；
- 双方序列化结果必须通过同一 fixture 快照。

最终使用 JSON Schema 还是其他 IDL：**建议 JSON Schema，待实现前审核**。

## 7. 稳定 ID 体系

### 7.1 ID 列表

| ID | 作用 | 生成方 | 是否可进入客户端 |
|---|---|---|---|
| `gameProfileId` | 本地或账号游戏档案 | 游戏/账号服务 | 可以 |
| `sessionId` | 一次病例会话 | 模型服务端 | 可以 |
| `caseId` | 病例逻辑标识 | 模型病例系统 | 可以，但不得携带诊断语义 |
| `caseVersion` | 病例不可变版本 | 模型病例系统 | 可以 |
| `npcId` | 地图 NPC 稳定标识 | 游戏内容系统 | 可以 |
| `patientRoleId` | 患者角色表现配置 | 模型或内容系统 | 只允许公开投影 |
| `interactionId` | 地图交互点 | 游戏内容系统 | 可以 |
| `locationId` | 场景或房间 | 游戏内容系统 | 可以 |
| `factId` | 病例事实 | 模型病例系统 | 只返回已经披露的 ID |
| `testId` | 医学检查类型 | 模型检查目录 | 可以 |
| `deviceId` | 游戏设备实例或类型 | 游戏经营系统 | 可以 |
| `criterionId` | 评分量表条目 | 模型评估系统 | 结果阶段按需公开 |
| `clientTurnId` | 玩家回合幂等键 | 游戏客户端 | 可以 |
| `clientRequestId` | 其他写操作幂等键 | 游戏客户端 | 可以 |
| `eventId` | 流式事件去重与恢复 | 模型服务端 | 可以 |
| `traceId` | 跨层诊断追踪 | 服务端入口 | 可以返回，但不得包含敏感信息 |

### 7.2 ID 规则

- ID 必须不透明、稳定、不可从中推断隐藏诊断。
- `caseId` 禁止使用 `lymphoma_001` 这类直接泄露答案的客户端值；服务端内部可有另一个私有标识。
- 显示名称可以修改，稳定 ID 不随翻译和文案修改变化。
- 进行中的会话始终绑定创建时的 `caseVersion`。
- 已发布病例版本不可原地覆盖；修订必须生成新版本。
- ID 字符集、最大长度和 UUID/ULID 选择：**待审核**。

## 8. 公共数据分类

### 8.1 四级分类

| 等级 | 示例 | 客户端规则 |
|---|---|---|
| Public | 地图、普通 NPC 名称、公开检查目录 | 可发布 |
| Client-visible | 初始主诉、已披露事实、已完成检查、结果摘要 | 仅按会话授权返回 |
| Server-confidential | 未披露事实、完整检查结果、答案、rubric、prompt | 永不进入客户端 |
| Secret | API key、数据库凭据、签名密钥 | 仅安全配置系统持有 |

### 8.2 客户端投影原则

客户端数据必须从 allowlist Schema 构造，禁止先取得完整病例对象再删除敏感字段。原因是新增字段、异常路径、日志或序列化错误都可能导致隐藏内容泄露。

必须扫描以下位置，确认不存在隐藏内容：

- `public/`；
- JavaScript bundle；
- source map；
- IndexedDB；
- localStorage/sessionStorage；
- Phaser cache；
- Tiled JSON；
- HTML；
- 客户端日志和错误上报；
- 网络响应和 SSE event；
- 导出的游戏存档。

## 9. 病例公共投影

### 9.1 CaseSummary

建议的最小结构：

```ts
type CaseSummaryV1 = {
  contractVersion: "1";
  sessionId: string;
  caseId: string;
  caseVersion: string;
  patientNpcId: string;
  title?: string;
  chiefComplaint: string;
  patientDisplay: {
    displayName: string;
    ageBand?: string;
    genderDisplay?: string;
    portraitAssetId?: string;
  };
  allowedActions: Array<
    "ask_patient" | "order_test" | "submit_diagnosis"
  >;
  sessionPhase: SessionPhaseV1;
};
```

注意：

- `title` 不得泄露诊断；
- `ageBand` 与精确年龄由病例设计决定；
- `portraitAssetId` 必须指向游戏侧允许使用的素材；
- 是否向客户端返回 `caseId`：**待安全审核**；如返回，必须是不透明 ID。

### 9.2 ClientCaseProjection

建议结构：

```ts
type ClientCaseProjectionV1 = {
  sessionId: string;
  caseVersion: string;
  initialPresentation: string;
  disclosedFacts: Array<{
    factId: string;
    displayText: string;
    disclosedAtTurn: number;
  }>;
  completedTests: TestResultV1[];
  turnCount: number;
  turnLimit?: number;
  sessionPhase: SessionPhaseV1;
};
```

禁止包含：

- `answerKey`；
- 未披露事实；
- 全部可申请检查及其隐藏结果；
- 完整 rubric；
- 教师备注；
- prompt；
- 模型内部推理；
- 安全策略细节。

## 10. 会话状态机

### 10.1 建议状态

```ts
type SessionPhaseV1 =
  | "created"
  | "active"
  | "awaiting_model"
  | "test_pending"
  | "diagnosis_submitted"
  | "evaluating"
  | "completed"
  | "expired"
  | "cancelled"
  | "failed";
```

### 10.2 状态说明

| 状态 | 含义 | 游戏层表现建议 |
|---|---|---|
| `created` | 会话已创建，尚未开始首轮 | 展示病例入口和初始主诉 |
| `active` | 可以问诊、申请检查或提交诊断 | 允许输入和相关交互 |
| `awaiting_model` | 正在处理问诊 | 锁定重复提交，允许取消展示但不一定取消服务端请求 |
| `test_pending` | 检查已接受但尚未完成 | 展示进度或推进游戏时间 |
| `diagnosis_submitted` | 已提交诊断，不再允许普通问诊 | 显示确认或结算过渡 |
| `evaluating` | 正在生成评分和复盘 | 展示可恢复加载状态 |
| `completed` | 已完成并有稳定结果 | 结果页和奖励换算 |
| `expired` | 服务端会话已过期 | 提示无法继续，保留本地历史摘要 |
| `cancelled` | 用户或系统取消 | 返回世界或保留未结算记录 |
| `failed` | 不可恢复失败 | 显示明确错误和支持信息 |

### 10.3 状态转换

```text
created → active
active → awaiting_model → active
active → test_pending → active
active → diagnosis_submitted → evaluating → completed
created/active/awaiting_model/test_pending → expired
created/active → cancelled
任意非终态 → failed
```

需要审核的问题：

- 是否允许提交诊断后撤回：**待审核**。
- 是否允许完成后继续自由问诊：**待审核**。
- 检查是否立即完成，还是受游戏时间影响：**待审核**。
- 模型请求取消后是否回滚回合计数：**待审核**。
- 会话默认过期时间：**待审核，留空：__________**。

## 11. API 基线

### 11.1 推荐端点

```text
GET    /api/game/cases/daily
POST   /api/game/sessions
GET    /api/game/sessions/:sessionId
POST   /api/game/sessions/:sessionId/turns

```

是否保留每日病例端点、是否需要账号鉴权：**待产品审核**。

### 11.2 通用请求头

建议：

### 11.4 问诊回合

```ts
type TurnRequestV1 = {

type TurnCompletedV1 = {
```

- 单次输入最大字符数：**待审核，留空：__________**。

- 多问题是否算一个回合：**待玩法与模型评测共同审核**。
- 闲聊是否消耗回合：**待审核**。

1. 游戏层先判断设备是否拥有、是否解锁、是否有足够游戏资源；

## 12. 流式事件协议

### 12.1 事件封套

```ts
type StreamEventEnvelopeV1<T> = {
  contractVersion: "1";
  eventId: string;
  eventType: string;
  sessionId: string;
  clientTurnId?: string;
  sequence: number;
  emittedAt: string;
  traceId?: string;
  payload: T;
};
```

### 12.2 建议事件

| eventType | 用途 | 是否持久化 |
|---|---|---|
| `turn.accepted` | 已接受回合 | 是 |
| `action.classified` | 已识别动作，可不向最终用户展示 | 建议服务端保存 |
| `patient.reply.delta` | 流式患者文本 | 可只保存聚合结果 |
| `patient.reply.completed` | 完整患者回复和披露事实 | 是 |
| `test.accepted` | 检查请求已接受 | 是 |
| `test.completed` | 检查完成 | 是 |
| `diagnosis.accepted` | 诊断已接受 | 是 |
| `evaluation.progress` | 结算进度 | 可选 |
| `evaluation.completed` | 最终结果 | 是 |
| `session.state_changed` | 会话状态变化 | 是 |
| `safety.interrupted` | 安全边界中断角色扮演 | 是，但日志需脱敏 |
| `request.error` | 请求失败 | 是，按日志策略脱敏 |

### 12.3 顺序和恢复

- 同一会话的 `sequence` 单调递增。
- 客户端按 `eventId` 去重。
- 断线重连是否支持 `Last-Event-ID`：**建议支持，待实现评估**。
- 流式 delta 不改变权威状态；只有 completed 事件提交最终状态。
- 客户端未收到 completed 时不得自行拼接并永久保存为正式回答。
- 服务端完成但客户端断线时，客户端应通过会话查询恢复最终状态。

## 13. 错误模型

### 13.1 通用结构

```ts
type SharedErrorV1 = {
  code: string;
  message: string;
  retryable: boolean;
  traceId?: string;
  details?: Record<string, unknown>;
};
```

`message` 用于用户或开发显示；业务逻辑必须依据稳定 `code`，不能解析自然语言。

### 13.2 建议错误码

| code | 含义 | retryable | 游戏侧建议 |
|---|---|---:|---|
| `INVALID_REQUEST` | Schema 或字段错误 | 否 | 阻止继续并记录客户端缺陷 |
| `UNSUPPORTED_CONTRACT_VERSION` | 契约不兼容 | 否 | 提示刷新或更新 |
| `SESSION_NOT_FOUND` | 会话不存在 | 否 | 提供重新开始入口 |
| `SESSION_EXPIRED` | 会话过期 | 否/按策略 | 保留本地摘要，不继续提交 |
| `INVALID_SESSION_STATE` | 当前状态不允许该动作 | 否 | 刷新状态并恢复 UI |
| `DUPLICATE_REQUEST` | 重复请求 | 是 | 读取首次请求结果，不重复扣费 |
| `TURN_LIMIT_REACHED` | 达到回合上限 | 否 | 引导提交诊断 |
| `TEST_NOT_AVAILABLE` | 病例无此检查 | 否 | 恢复检查 UI |
| `TEST_ALREADY_COMPLETED` | 检查重复 | 是 | 直接展示已有结果 |
| `DIAGNOSIS_ALREADY_SUBMITTED` | 已提交诊断 | 否 | 进入结算/结果状态 |
| `MODEL_TIMEOUT` | 模型超时 | 是 | 保留输入并允许重试 |
| `MODEL_UNAVAILABLE` | 模型服务不可用 | 是 | 暂停病例，不伪造回复 |
| `STREAM_INTERRUPTED` | 流式传输中断 | 是 | 查询权威会话状态 |
| `SAFETY_REAL_HEALTH_INPUT` | 检测到真实个人健康咨询 | 否 | 退出角色并展示安全提示 |
| `SAFETY_PROMPT_INJECTION` | 索要答案或覆盖角色 | 按策略 | 显示角色内拒绝或安全提示 |
| `INTERNAL_ERROR` | 未分类内部错误 | 是 | 通用错误，展示 traceId |

错误码命名最终规范和 HTTP 状态映射：**待实现前审核**。

## 14. 幂等、重试和并发

### 14.1 幂等

- 创建会话、问诊、检查、诊断和取消均携带客户端生成的幂等 ID。
- 同一会话中重复提交相同幂等 ID，应返回首次操作的同一逻辑结果。
- 重复请求不得产生第二次模型调用、检查扣费、回合增加或奖励发放。
- 幂等记录保留时间：**待审核，留空：__________**。

### 14.2 重试

- 只对 `retryable: true` 的错误自动或手动重试。
- 自动重试必须有次数、退避和总时长上限。
- 流式中断后优先查询权威状态，不直接重复模型调用。
- 诊断和奖励属于高风险写操作，客户端不得在未知结果时盲目重提。

### 14.3 并发

- 一个会话默认只允许一个活动问诊生成请求。
- 检查是否允许并行：**待玩法审核**。

## 15. NPC 与病例绑定

### 15.1 拆分原则

患者 NPC 不是一个跨层共享对象，而是两个对象的绑定：

```text
游戏对象
  npcId、mapId、position、sprite、animation、interactionId

模型对象
  sessionId、caseId、caseVersion、patientRoleId、persona、facts

共享绑定
  npcId + sessionId + patientRoleId
```

### 15.2 绑定生命周期

1. 游戏层在场景中生成患者 NPC；
2. 玩家触发交互；
3. 游戏层创建或恢复病例会话；
4. 服务端返回 `sessionId` 和允许展示的患者信息；
5. 游戏层把本地 `npcId` 与 `sessionId` 绑定；
6. 交互过程中所有医学动作使用 `sessionId`；
7. 会话完成后游戏层只保存必要关联和结果摘要。

是否允许同一个 NPC 承载多个病例、每日病例更换后如何显示：**待内容设计审核**。

## 16. 检查设备与医学检查

### 16.1 双 ID 模型

- `deviceId`：游戏世界中的设备或设备类型，属于经营系统。
- `testId`：医学检查目录中的检查类型，属于模型系统。

示例映射：

```ts
type DeviceTestMappingV1 = {
  deviceId: string;
  supportedTestIds: string[];
  mappingVersion: string;
};
```

### 16.2 权限顺序

```text
游戏经营校验
  是否拥有设备、是否解锁、费用和时间是否允许
      ↓
模型会话校验
  当前病例是否支持、是否重复、结果是否存在
      ↓
返回接受、等待或完成
      ↓
游戏层提交经营状态变化
```

扣费采用预扣、成功后扣费还是失败退款：**待经营设计审核**。无论采用哪种方式，都必须可通过 `clientRequestId` 防止重复扣费。

## 17. 医学评分与游戏奖励

模型层输出医学评分，不输出游戏奖励。共享层只规定转换输入：

```ts
type RewardInputV1 = {
  evaluationId: string;
  sessionId: string;
  scoreTotal: number;
  diagnosisCorrect: boolean;
  criterionOutcomes: Array<{
    criterionId: string;
    outcome: "met" | "partial" | "missed" | "not_applicable";
  }>;
};
```

游戏层根据自身版本化规则生成：

- 经验；
- 金钱；
- 声望；
- 成就；
- 设备或场景解锁；
- 每日挑战奖励。

禁止把 LLM 生成的自然语言作为奖励计算输入。奖励计算只消费有限、稳定、可验证的结构化字段。

奖励公式、失败奖励、重复病例奖励衰减：**待游戏设计审核**。

## 18. 本地存档与服务端会话

### 18.1 游戏层本地存档可保存

- `gameProfileId`；
- 游戏进度、地图位置、任务和经营状态；
- `sessionId`、`caseVersion`、`sessionPhase` 的必要镜像；
- 已经展示给玩家的对话和检查结果缓存；
- 最终结果摘要；
- 游戏内容 build ID 和共享契约版本。

### 18.2 本地存档不得保存

- 完整病例；
- 未披露事实；
- 答案键；
- rubric；
- prompt；
- 模型密钥；
- 服务端安全判断细节。

### 18.3 恢复流程

```text
读取本地存档
→ 检查 save schema 和 content build
→ 使用 sessionId 查询服务端权威状态
→ 比较 caseVersion 和 contractVersion
→ 合并允许展示的投影
→ 恢复 UI 或进入过期/不兼容处理
```

离线状态下是否允许浏览历史已披露内容：**建议允许，待隐私审核**。

服务端会话被删除而本地仍有记录时：**待产品审核**。

## 19. 版本体系

至少存在以下独立版本：

| 版本 | 所有者 | 作用 |
|---|---|---|
| `contractVersion` | 共享层 | 公共 API 和 DTO |
| `schemaVersion` | 共享层/各数据域 | 具体数据结构 |
| `eventVersion` | 共享层 | 流式事件协议 |
| `caseVersion` | 模型层 | 病例不可变版本 |
| `promptVersion` | 模型层 | 模型行为追溯 |
| `modelVersion` | 模型层 | 模型供应商和模型版本 |
| `evaluationVersion` | 模型层 | 评分逻辑和 rubric |
| `contentBuildId` | 游戏层 | 游戏素材和地图内容 |
| `saveSchemaVersion` | 游戏层 | 本地存档迁移 |
| `rewardRuleVersion` | 游戏层 | 医学评分到奖励的换算 |

### 19.1 兼容原则

- 新增可选字段通常视为向后兼容。
- 删除字段、修改含义、改变枚举或单位属于破坏性变化。
- 破坏性变化必须提升 contract major version。
- 双方必须在构建时声明支持的契约范围。
- 进行中的会话固定创建时的病例和评估版本。
- 历史回放使用历史 Schema 或明确迁移器，不能静默套用当前逻辑。

当前已批准例外：对话架构 C0–C7 期间继续使用公共 `1` / `v1-rc1` 标签。C5 的必填 `TurnCompletedV1.effects` 因此是一次明确记录的不兼容原地升级；旧 RC 产物保持 `superseded`，双方必须重新构建 adapter、运行契约测试，并在 C7 重新生成发布证据。该例外不改变后续稳定版本默认遵循 major-version 规则。

## 20. 安全与可信边界

### 20.1 基本原则

- 病例数据是数据，不是可执行指令。
- 玩家输入是不可信输入。
- 模型输出也是不可信输入，必须经过 Schema 和业务校验。
- 客户端永远不被视为评分、防作弊或病例保密的可信来源。
- 所有正式答案和评分由服务端计算并记录。

### 20.2 真实健康信息

当玩家开始描述自己的真实症状、急症、自伤或其他高风险情形时，模型层应返回结构化安全中断；游戏层负责显示适当提示并停止角色扮演。

具体提示文案、地区化急救信息、年龄限制和日志保留策略：**需要医学、法律和隐私审核，留空：__________**。

### 20.3 提示注入

需要覆盖：

- 索要标准答案；
- 要求显示 system prompt；
- 要求忽略患者角色；
- 将病例字段伪装成指令；
- 多轮诱导模型泄露未披露事实；
- 要求模型伪造检查结果；
- 要求修改评分或奖励。

安全策略不能只存在于 prompt；还必须有服务端数据权限、事实白名单和输出验证。

## 22. 契约测试

### 22.1 双方必须共同通过

- 所有公共 fixture 的请求和响应均通过 Schema。
- TypeScript 与未来 Python 表示序列化后语义一致。
- unknown、absent、present 不混淆。
- 重复幂等请求不产生第二次副作用。
- 状态机拒绝非法动作。
- 流式事件顺序可恢复且可去重。
- 客户端投影不包含隐藏字段。
- 诊断重复提交不会重复结算或发奖。
- 检查重复申请不会重复扣费。
- 历史病例版本可正确恢复或得到明确不兼容结果。
- 所有错误码都有确定的游戏侧表现。

### 22.2 游戏侧额外验证

- mock 模型下完整闭环可玩；
- 模型超时不导致角色永久锁死；
- 刷新后能从 IndexedDB 和服务端恢复；
- DOM 输入与 Phaser 键盘控制互不干扰；
- 客户端构建扫描不到答案和 rubric；
- 评分字段变化通过 adapter 转换，不直接破坏奖励系统。

### 22.3 模型侧额外验证

- headless runner 可完成完整病例；
- Patient 只使用 allowed facts；
- 检查结果完全来自病例包；
- 诊断判定有结构化依据；
- 真实健康输入和提示注入按协议处理；
- 固定病例重复运行的一致性达到门槛；
- 模型不可用时返回错误，不生成伪造内容。

- 模拟经营至少包含一种奖励和一种解锁。
- 存档可以刷新恢复并通过迁移测试。
- 超时、断流、错误、过期会话均有可恢复 UI。
- 游戏侧全部契约测试通过。

### 24.2 模型层门槛

- 至少 5 个经双 AI 交叉验证的 published 病例完成 headless 闭环；MVP 扩充目标为 20–50 个。
- Controller、Patient、Evaluator 的数据权限隔离可证明。
- 固定检查结果不由 LLM 生成。
- 诊断和轨迹评分有逐项结构化依据。
- 提示注入、答案泄露、unknown/absent、一致性测试达到门槛。
- 模型超时和失败可以恢复或明确终止。
- 模型侧全部契约测试通过。

### 24.3 共享层门槛

- contract v1 冻结并有变更记录。
- 所有公共 Schema 有正反例 fixture。
- mock server 与 headless client 均使用同一契约。
- 状态机、错误码、幂等和流式恢复已经测试。
- 客户端投影通过隐藏信息扫描。
- 版本兼容矩阵可读且双方声明支持范围。
- 双方独立 CI 均能运行共享契约测试。

### 24.4 医学与产品门槛

- 病例、答案和 rubric 已有与 `caseVersion + contentHash` 精确绑定的双 AI 交叉验证记录。
- 产品明确标注教育/娱乐用途。
- 真实健康输入处理通过医学与法律审核。
- 数据和开源许可证台账完成。
- 评分如何转换为经营奖励已经确定。
- MVP 范围、目标用户、年龄和地区：**待审核**。

## 25. 合并进入统一 MVP 的过程

建议按以下顺序：

1. 冻结 `share` contract v1；
2. 固定一组双方都通过的 fixture；
3. 在集成分支接入真实模型 adapter，但保留 mock adapter；
4. 只接入一个代表性病例，不立即接入全部病例；
5. 验证问诊流式响应、检查、诊断和结果；
6. 验证模型失败、断网、刷新、存档恢复和重复请求；
7. 扫描客户端构建，确认无隐藏内容；
8. 验证医学评分到游戏奖励的转换；
9. 扩展到 5 个双 AI 交叉验证病例做回归；
10. 达到性能、成本和安全门槛后扩展到 MVP 病例池。

合并后的物理目录结构有两个候选：

### 方案 A：继续保留三个 package

```text
apps/game/
├─ game/
├─ model/
├─ share/
└─ integration host
```

优点：边界清楚、可分别测试。缺点：部署和 workspace 配置更复杂。

### 方案 B：同一 Next 应用内逻辑分包

```text
apps/game/
├─ app/
├─ game/
├─ model/
└─ share/
```

优点：MVP 部署简单。缺点：需要依赖规则和测试防止重新耦合。

## 29. 当前结论

前期采用以下工作方式：

```text
game/  独立开发可玩的二维世界、模拟经营和完整 mock 游戏闭环
model/ 独立开发结构化病例、受控虚拟患者和 headless 医学闭环
share/ 维护双方唯一共同依赖的契约、Schema、fixture、mock 和测试
```

只有当两边分别完成独立闭环、共同通过 contract v1、隐藏信息检查、失败恢复测试和病例双 AI 交叉验证后，才进入统一 MVP 合并开发。人工审核或签字不构成合并阻塞。

本文保留的所有空位都属于真实待决问题。审核时应填写、删除或改写这些空位；在审核完成前，开发实现不得默认为某个未决定答案。
