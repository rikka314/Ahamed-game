## 1. 用途与读取规则

本文件用于代替“每次任务都完整读取全部 baseknowledge”的旧流程。它只保留项目当前状态、三层边界、关键技术决策、安全约束和长文档路由，不取代长文档中的详细设计。

每次在本项目工作时：

1. 完整读取项目根 `AI_CONTEXT.md`，确认当前已经实现到哪里；
2. 完整读取本文件，建立项目全局心智模型；
3. 根据第 8 节判断任务属于游戏层、模型层、共享层还是跨层任务；
4. 只完整读取与任务直接相关的长文档；
5. 普通单层任务不得因为“可能有用”而默认读取其余长文档。

只有以下情况需要完整读取三份长文档：

- 用户明确要求全量审核、总体架构复核或重新划分三层；
- 任务会同时改变游戏、模型和共享契约；
- 多份文档出现冲突，且压缩上下文无法确定优先级；
- 需要重写本压缩上下文本身，并核对三份来源文档是否仍然一致。

发生冲突时，当前实现状态以 `AI_CONTEXT.md` 为准；目标技术设计以对应层长文档为准；跨层接口和安全边界以 `共享层基本内容.md` 为准。

## 2. 项目一句话定义

AhaMed Doctor Game 是面向桌面浏览器与 Android 的单人俯视 2D 像素模拟医生游戏：玩家在诊所世界中移动、与患者和设备交互，通过自由问诊、申请检查和提交诊断完成“猜病”，再把医学评分转换为经营奖励、升级和内容解锁。iOS 不属于当前交付或人工验收范围。

产品是虚构病例的医学教育与娱乐模拟，不用于真实患者诊断、治疗、处方或急诊分流。

## 4. 三层所有权

| 层 | 负责 | 不负责 |
|---|---|---|
| `game/` 游戏层 | 2D 世界、地图、移动、NPC 表现、交互 UI、设备表现、模拟经营、奖励换算、输入、音频、本地存档 | 病例真相、答案、rubric、模型 prompt、医学评分裁判 |
| `model/` 模型层 | 病例包、事实披露、患者模拟、检查医学结果、诊断判定、轨迹评分、安全、模型调用与观测 | 玩家逐帧移动、地图渲染、经营资产、奖励和解锁 |
| `share/` 共享层 | DTO、JSON Schema、稳定 ID、状态机、API、流式事件、错误码、fixture、mock、版本和契约测试 | Phaser/React 实现、模型 SDK、数据库实体或任一侧业务内部实现 |

允许的依赖只有：

```text
game  ──依赖──> share <──依赖──  model
```

游戏层和模型层不得直接引用对方内部模块。即使 MVP 最终同进程部署，这个逻辑边界仍然保留。

## 5. 游戏层基线摘要

详细文档：`技术栈.md`

- 正式平台是 Web-first 单人游戏，当前发布与真机范围为桌面浏览器和 Android，完整体验以 WebGL 为验收目标；原 Godot 3D 基线已经撤销。
- 目标组合是 Next.js 16 + React 19 + TypeScript + client-only Phaser 4.2.1。
- Phaser 负责世界、Tilemap、角色、碰撞、相机和轻量场景提示；React/DOM 负责问诊、检查选择、诊断、设置、结果和无障碍交互。
- React 不同步逐帧坐标；跨边界只发送稳定、可序列化的业务事件。Phaser 必须在组件卸载时销毁，并兼容 React Strict Mode 重挂载。
- 正式地图采用 Tiled 1.12.2 JSON；使用稳定 `mapId`、`npcId`、`interactionId`，不把 Tiled GID、数组下标或 Phaser 对象 ID 写进长期存档或共享契约。
- 物理使用 Arcade Physics；MVP 不引入 Matter.js、ECS、自制引擎或第二套游戏运行时。
- 模拟经营规则放在纯 TypeScript domain 中，包括 economy、inventory、facilities、reputation、quests、calendar、rewards 和 progression；LLM 不决定经营状态。
- 本地存档目标是 IndexedDB + 版本化 `SaveEnvelope` + 迁移 + 导入导出；客户端存档不是正式评分、防作弊或隐藏病例的可信来源。
- 先做代表性诊室 PoC，再批量制作地图和美术；PoC 必须覆盖移动、碰撞、遮挡、NPC、交互、转场、响应式缩放和移动端性能。
- 测试以 Vitest 规则测试、Playwright 浏览器闭环和移动真机 smoke 为主。

## 6. 模型层基线摘要

详细文档：`开源资源与技术方案.md`

- 核心产品形态是虚拟标准化病人：玩家自由问诊、申请检查、提交主要诊断和可选鉴别诊断，系统返回结构化评分与复盘。
- 病例包是唯一事实源。病例事实至少区分 `present`、`absent`、`unknown`，并设置 `spontaneous`、`if_asked`、`test_only`、`hidden` 等披露条件。
- 在线职责拆成单一 Patient Agent、确定性 Test/Measurement 与 Evaluator；MVP 可用同一基础模型配合不同 prompt、上下文和数据权限，不要求多套模型。
- Patient Agent 负责问诊、闲聊和检查意图的语义理解，只能看到完整安全病例视图；检查结果确定性读取病例包；Evaluator 输出诊断与过程评分证据。Controller 不参与在线逐轮路由。
- 默认使用 Schema、fact-ID、状态与泄露校验器；Consistency LLM 只在评测证明必要时作为可选回退。
- 病例必须离线生产：合成/授权来源 → Case Builder → 中文化 → 独立 AI 临床安全校验 + 独立 AI 诊断质量校验 → 冻结版本。禁止玩家打开页面时临场生成完整随机病例。
- 优先借鉴 PatientHub 的角色隔离与评测接口、EasyMED 的职责拆分、AgentClinic 的检查协议、MedSP1000 的角色包与冻结 rubric；不整仓采用研究运行时。
- 病例骨架优先考虑 DDXPlus、Synthea；术语可参考 Disease Ontology、Mondo、HPO、ICD-11。代码许可不自动授权病例数据。
- 不直接公开使用来源或再分发权不明确的真实医患对话、医院病历、MIMIC/NEJM 等受限病例内容。
- MVP 目标是 20–50 个经双 AI 交叉验证的冻结病例、每局约 15–20 轮；先以至少 5 个病例完成 headless 与安全回归门槛。

## 7. 共享层基线摘要

详细文档：`共享层基本内容.md`

- 每项状态只有一个权威所有者：位置和经营属于游戏层；完整病例、已披露事实、检查结果和医学评分属于模型层；契约版本属于共享层。
- 客户端只接收 allowlist 投影。未披露事实、答案、rubric、prompt、模型密钥和内部推理永不进入浏览器 bundle、资源、日志或 IndexedDB。
- 核心稳定 ID 包括 `sessionId`、不透明 `caseId`、`caseVersion`、`npcId`、`interactionId`、`factId`、`testId`、`deviceId`、`clientTurnId`、`clientRequestId`、`eventId` 和 `traceId`。
- 建议会话阶段为 `created`、`active`、`awaiting_model`、`test_pending`、`diagnosis_submitted`、`evaluating`、`completed`、`expired`、`cancelled`、`failed`。
- API 覆盖病例选择、创建/查询会话、问诊、检查、诊断、结果和取消；流式协议使用带版本、顺序号、事件 ID 与 trace ID 的事件封套。
- 所有写操作使用幂等 ID。重复请求不得引发第二次模型调用、回合增加、检查扣费、诊断结算或奖励发放。
- `deviceId` 属于游戏经营系统，`testId` 属于医学检查目录；双方分别校验，但任何失败路径都必须避免重复扣费。
- 模型只输出结构化医学评分；游戏层用版本化规则把评分转换为经验、金钱、声望、成就和解锁。禁止用 LLM 自然语言直接发奖。
- 共享层应提供同一套 JSON Schema、fixture、mock model server、headless game client、contract tests、兼容矩阵和变更记录。
- MVP 合并前必须证明：游戏层可用 mock 完成完整可玩闭环；模型层可用 headless client 完成医学闭环；双方共同通过 contract v1、隐藏信息扫描、失败恢复和病例双 AI 交叉验证。

## 9. 不可破坏的约束

- `game/` 与 `model/` 前期独立开发，只通过 `share/` 契约连接。
- 隐藏病例、答案、rubric、生产 prompt 和模型密钥不得进入客户端。
- 检查医学结果来自双 AI 交叉验证的冻结病例包，不由在线 LLM 临场编造。
- LLM 输出必须经过 Schema 和业务验证；模型输出本身不是可信输入。
- LLM 不直接修改货币、经验、库存、时间、设备或解锁。
- fixture 不得包含真实患者数据、生产密钥、生产 prompt 或未获授权病例。
- 产品不得向玩家提供真实个人疾病诊断、处方或治疗建议；真实健康输入需要结构化安全退出。

## 10. 仍待审核的关键决策

- contract/Schema 生成工具、ID 格式、SSE 恢复窗口、幂等保留时间和兼容弃用窗口。
- 游戏经济曲线、设备价格与耗时、评分到奖励公式、每局回合上限。
- 正式逻辑分辨率、tile 尺寸、性能预算和美术规范。
- MVP 合并后继续保留三个 package，还是在同一 Next 应用内逻辑分包。
