## 1. 背景与问题判断

当前实现把外部模型主要当作“对话措辞生成器”，真正的医学追问、事实选择和回复控制仍由本地逻辑承担。这导致模型没有真正扮演一个拥有完整人格、理解上下文且受病例约束的患者。

现有问题主要表现为：

- Controller 先在本地选择事实，Patient 模型只能围绕局部结果生成文本。
- 即使 Patient 模型生成了自然回复，服务端仍可能用本地模板重新渲染并覆盖模型输出。
- 闲聊、问候、抱怨等非医学输入可能不进入 Patient 模型，只得到固定本地回复。
- “现在还这样么”之类依赖上下文的追问无法仅靠关键词或规则稳定理解。
- “量一下体温”“做个胸片”等自然语言无法形成可靠的检查动作。
- 用户直接询问尚未完成的检查结果时，系统缺少“尚未检查—询问是否执行—确认后执行”的连续状态。
- Patient 模型没有持续获得完整人格、安全病例事实、最近对话、已披露事实和检查状态，因此无法像正常人一样自然交流。

用户测试中出现的下列现象，本质上都来自上述架构问题：

- “现在还这样么”在模型失败后返回 `MODEL_UNAVAILABLE`。
- “现在还是有这样的症状么”被降级为固定的“我在听，医生”。
- “量一下体温”没有触发检查，只得到社交兜底回复。

本轮重构不再继续扩充本地敏感词、关键词路由或固定问答模板，而是把 Patient AI 提升为在线对话的唯一语义理解与患者回复主体；本地只负责安全边界、事实权限、状态管理和确定性工具执行。

## 2. 重构目标

目标交互链路如下：

```text
玩家输入
  → 本地现实健康 / 危机 / 提示注入边界
  → 组装安全病例视图与会话记忆
  → 单一 Patient Agent 理解并生成结构化响应
       ├─ 普通问诊
       ├─ 闲聊与情绪互动
       ├─ 检查结果询问
       ├─ 检查执行请求
       └─ 建议稍后执行某项检查
  → 服务端验证事实引用和工具动作
  → 原子执行检查工具
  → 返回患者回复 + 独立检查报告
```

每一轮 Patient Agent 可以看到：

- 三种人格模板之一，以及当前病例允许公开的社交背景。
- 全部非隐藏、非 `test_only` 的患者可回答事实。
- 检查项目 ID、中文名、别名与当前完成状态。
- 仅限已经完成的检查报告。
- 全部已提交对话轮次；每轮都重新传入，不依赖模型自行跨请求记忆。
- 已披露事实集合。
- 连续离题轮数。
- 当前待确认的检查建议。

Patient Agent 永远不能看到：

- 标准答案、目标诊断和评分规则。
- 隐藏事实。
- 尚未完成的检查结果。
- 评分证据、奖励或其他会导致剧透的内部字段。

## 3. 已确认的架构决策

1. 在线问诊链路只保留一个 Patient Agent，不再让 Controller 参与逐轮路由、事实选择或回复生成。
2. 每轮向 Patient Agent 提供完整的安全病例视图，不引入关键词检索、向量检索或传统 RAG 截断。
3. 明确的自然语言检查指令可以直接执行检查；单纯询问检查结果不能自动执行检查。
4. 检查完成后的界面输出由两部分组成：患者自然语言回应，以及独立的系统检查报告。
5. 首版只提供三种人格模板：温和配合型、焦虑求安慰型、急躁直接型；后续通过注册表继续扩充。
6. 外部模型失败时最多进行一次受控重试，仍失败则返回明确错误；不得用本地模板伪造患者回答。
7. 保留现有公共契约版本标识 `v1-rc1`，即使本轮属于不兼容的原地升级；旧 RC 产物必须标记为已被替代，并重新生成全部哈希与验收证据。
8. 最终诊断通过 `/diagnose`、未来明确的 UI 操作，或 Patient AI 对普通自然语言的结构化意图判断提交。玩家以肯定、结论性表达给出唯一主诊断时启动评分；同时提到多个疾病时，只有能识别出唯一主诊断才提交，其余作为鉴别诊断，否则继续对话。

### C1：病例人格与安全病例视图

首版人格模板：

1. `gentle_cooperative`：温和、礼貌、愿意配合；连续离题 3 轮后自然提醒尽快看病。
2. `anxious_reassurance_seeking`：容易担忧，会主动确认严重程度；连续离题 2 轮后表达焦虑并拉回病情。
3. `impatient_direct`：表达简短直接，不喜欢长时间闲聊；连续离题 1 轮后催促继续问诊。

首批病例默认分配：

- C01、C04：`gentle_cooperative`
- C02、C05：`anxious_reassurance_seeking`
- C03：`impatient_direct`

病例数据新增：

- `personaTemplateId` 与人格模板版本。
- 学业或职业背景。
- 日常生活背景。
- 最多 3 项兴趣爱好。
- 检查项目中文名和自然语言别名。
- 每个病例允许配置的表达习惯或语言特征。

实现统一的 `SafePatientCaseView`，内容包括：

- 所有允许患者直接回答的病例事实。
- 尚未完成检查的名称、别名和状态，但不包含结果。
- 已完成检查的确定性报告。
- 人格、社交背景和表达约束。

必须排除：

- 目标诊断、答案、评分标准和评分证据。
- 隐藏事实。
- 尚未完成检查的结果。
- 任何只供系统评估使用的内部字段。

退出标准：

- 5 个病例全部通过新 schema 校验与哈希校验。
- 安全病例视图的泄漏测试通过。
- 三种人格至少各有一个可运行病例示例。

### C2：单一 Patient Agent 契约

移除在线问诊链路中的 Controller，新增统一输入契约：

```ts
interface PatientAgentInput {
  userText: string;
  patientProfile: PatientProfile;
  safeCaseView: SafePatientCaseView;
  recentTurns: CommittedTurn[];
  disclosedFactIds: string[];
  completedTests: TestResultV1[];
  consecutiveOffTopicTurns: number;
  pendingTestSuggestionId?: string;
}
```

Patient Agent 必须输出结构化结果：

```ts
interface PatientAgentOutput {
  reply: string;
  interactionKind:
    | "medical_chat"
    | "social_chat"
    | "test_query"
    | "test_order";
  factIdsUsed: string[];
  personaFactIdsUsed: string[];
  completedTestIdsUsed: string[];
  requestedTestId?: string;
  suggestedTestId?: string;
  newFactsClaimed: string[];
  diagnosisLeak: boolean;
}
```

契约规则：

- 所有正常聊天轮次的最终患者回复均由 Patient Agent 生成。
- 社交聊天允许 `factIdsUsed`、`personaFactIdsUsed` 和 `completedTestIdsUsed` 为空。
- 所有引用 ID 必须来自本轮 `SafePatientCaseView`。
- `completedTestIdsUsed` 只能引用已完成检查。
- `requestedTestId` 表示玩家明确要求现在执行检查。
- `suggestedTestId` 表示患者理解了检查意图，但仍在等待玩家确认。
- 普通聊天不得自动提交最终诊断；CLI 在进入 Patient Agent 前只把单独病例诊断术语或“最终诊断：……”识别为明确的诊断动作。

退出标准：

- Provider、schema、prompt 和 deterministic mock 使用同一套输入输出契约。
- 契约解析失败、未知字段、未知 ID 和越权引用均有自动化测试。

### C3：Patient Agent 对话与检查工具循环

状态：**已完成（2026-08-28）**。自然语言直接执行、未完成结果询问、跨重启确认、重复幂等、`test_unavailable`、聊天与 `/test` 同源结果及崩溃恢复单次提交均已有自动化测试。

建立以下检查状态机：

```text
未检查
  ├─ 明确执行指令 → 执行中 → 已完成
  └─ 仅询问结果 → 等待确认 → 用户确认 → 执行中 → 已完成
```

具体行为：

- 玩家说“量一下体温”“做个胸片”等明确执行指令时：
  - Patient Agent 生成患者回应并返回 `requestedTestId`。
  - 服务端验证检查 ID 后，在同一个幂等操作中执行确定性检查。
  - 客户端依次展示患者回应和独立检查报告。
- 玩家问“你的 CT 结果怎么样”，但 CT 尚未完成时：
  - 不得执行 CT。
  - 患者说明自己还没有做，并询问是否现在去做。
  - 会话保存 `pendingTestSuggestionId`。
- 玩家下一轮说“好”“去做吧”等确认表达时：
  - Patient Agent 根据最近上下文和待确认检查返回 `requestedTestId`。
  - 服务端原子执行检查。
- 检查已经完成时：
  - Patient Agent 可以看到并引用对应报告。
- 用户询问病例中不存在的检查时：
  - 不生成检查结果，不产生工具动作。
  - 患者只说明当前没有该项结果，或请求医生进一步说明。

退出标准：

- 自然语言执行、结果询问、二次确认、重复执行和中断恢复测试全部通过。
- 同一个操作 ID 不会重复生成检查结果或重复提交对话。

### C4：真正使用 AI 回复并重建输出门控

状态：**已完成并于 2026-08-29 纠偏**。在线回复直接采用通过结构、授权引用、检查状态和泄漏门的 Patient Agent 文本；已删除安全源文本锚点、固定非事实短语白名单、关键词问答和本地患者渲染器。服务层结构或解析输出拒绝后只进行一次带 `regenerationInstruction` 的定向再生成，第二次失败时保持会话可继续且不提交业务状态。

删除远程模型成功后再由本地模板重新渲染患者回答的路径。

新的输出原则：

- 问候、闲聊、抱怨、玩笑、医学追问和检查请求均进入 Patient Agent。
- Patient Agent 的 `reply` 通过服务端验证后，原样保存并展示。
- 本地代码不再替换措辞，也不再根据关键词拼接固定患者文本。

服务端门控规则：

- 社交聊天允许不引用医学事实。
- 拒绝未知事实 ID、未知人格事实 ID 和未知检查 ID。
- 拒绝引用尚未完成的检查结果。
- 拒绝使用病例未授权的社交背景。
- 拒绝泄漏目标诊断、答案或评分内容。
- `newFactsClaimed` 必须为空；模型不得补造病例事实。
- “不知道”“没做过”“不清楚”不得被门控器错误解释为“正常”或“阴性”。
- 结构化输出不合格时，允许使用同一 Provider 进行一次定向再生成。
- 再生成仍失败时，不得回退到本地伪造患者回复。

Provider 失败处理：

- 保留现有最多一次重试策略。
- 最终失败返回 `MODEL_UNAVAILABLE`。
- 会话保持可继续使用。
- 失败轮次不得提交对话、披露事实或执行检查。
- 不产生“我在听，医生”之类本地伪患者回答。

退出标准：

- 每一条用户可见的患者发言都能追溯到一个通过验证的 Patient Agent 输出。
- 在线问诊链路不再调用本地患者回复模板。

### C5：会话、SQLite 与共享契约原地升级

状态：**已完成（2026-08-28）**。公共 DTO/Schema/fixture、模型 adapter、CLI 展示与 SQLite v6 已同步；历史轮次和幂等响应缺少 `effects` 时归一化为空数组，旧 validated buffer 仍可恢复。

```ts
effects: Array<
  | { type: "test_completed"; result: TestResultV1 & { status: "completed" } }

>;
```

会话状态新增：

- `consecutiveOffTopicTurns`
- `pendingTestSuggestionId`
- `interactionKind`
- 本轮引用的人格事实、病例事实和已完成检查 ID
- 本轮检查副作用

SQLite 迁移到 schema v6：

- 历史轮次缺少 `effects` 时按空数组读取。
- 人格从当前病例模板重新派生，不信任旧快照中的临时字段。
- 旧 operation buffer 可以继续恢复。
- 新写入统一使用新契约形状。

`/test` 命令继续保留为调试和兼容入口，但必须复用同一个确定性检查引擎，不维护第二套检查逻辑。

退出标准：

- 新建会话、恢复会话、崩溃恢复、幂等重放和旧数据库迁移测试全部通过。

### C6：CLI 体验验收

状态：**已完成 AI 主导的用户验收纠偏（2026-08-29）**。旧三人格 36 轮 deterministic CLI 旅程不再作为产品体验验收，只保留为历史回归数据。当前可玩 CLI 拒绝 `deterministic`，只允许真实 OpenAI-compatible Patient Agent；每轮向模型发送全部已提交对话历史。病例 `patientDisplayName` 仅作场景称呼或姓氏提示，医疗事实和显式年龄/性别等人格锚点仍是硬约束；病例未提供的完整姓名、家庭成员姓名、住址、普通日常经历等非医疗角色信息由 AI 自主合理补全，一旦补全即通过完整历史保持后续一致。输出门拒绝“病例没有说明”“资料未提供”等破坏沉浸感的幕后表述，并只允许一次真实 Provider 定向再生成，不提供任何本地固定患者答案。Patient Agent v0.4 同时输出 `diagnosisIntent`：AI 只根据玩家本轮原话判断是否已经明确唯一主诊断并提取主诊断、鉴别诊断或未提交候选，服务端验证所有词都来自原话；正确性仍交给既有本地评分器。CLI 已删除病例诊断词表和固定句式路由。真实 `gpt-5.6-sol` smoke 已验证“我确定就是普通感冒”和原问题句“是普通感冒吧，吃点药就好了”都会直接评分，“主诊断是普通感冒，流行性感冒和急性咽炎作为鉴别”按主次评分，而“这是普通感冒、流行性感冒、急性咽炎”因无主次保持 active 并继续自然对话。Provider 失败仍不生成伪患者回复或业务提交。模型层全量测试为 331/331，覆盖率门全部通过。

至少使用以下连续对话作为基础验收脚本：

```text
你好
请问有什么症状么
现在还这样么
今天天气不错
你平时喜欢做什么
现在还是有这样的症状么
量一下体温
你的CT结果怎么样
好，那去做吧
```

预期行为：

- 从问候到医学追问始终是同一个患者人格。
- “现在还这样么”能结合最近对话回答，不依赖固定关键词命中。
- 离题聊天得到自然回应，不再统一返回“我在听，医生”。
- 达到不同人格的离题阈值后，患者以符合人格的方式提醒继续看病。
- “量一下体温”产生患者回应和确定性体温报告。
- 尚未完成 CT 时不得展示 CT 结果。
- “好，那去做吧”能够确认并执行上一轮建议的 CT。
- Provider 失败时只显示明确错误，不出现本地伪患者回复。

退出标准：

- 三种人格各完成至少一段 12 轮以上 CLI 对话旅程。
- 对话连续性、人格一致性、检查状态和失败行为均符合预期。

## 7. 非目标与默认边界

- 首版不做流式输出。完整结构化结果必须先通过门控，再展示给用户。
- 首版不引入向量数据库或传统 RAG；病例规模允许每轮提供完整安全病例视图。
- 普通自然语言统一先进入 Patient Agent；只有 AI 明确认定玩家已提交唯一主诊断且服务端验证提取词来自本轮原话时，才执行最终诊断提交。不得用病例答案词表或固定句式替代这项语义判断。
- 不保留本地患者回复 fallback；本地只可返回系统错误或检查报告。
- 默认在线链路不增加第二个“一致性审查模型”，由确定性服务端门控负责校验。
- 首版只实现三种人格，但人格注册表和病例绑定字段必须允许后续扩充。
- 按已确认决策继续使用 `v1-rc1` 标签；由于接口和行为发生不兼容变化，必须归档旧产物并完整重做发布证据。
