# 游戏、模型与共享连接层分层及 LLM 架构研究总结

> 研究归档日期：2026-08-24
>
> 研究范围：AhaMed Doctor Game 的二维游戏工程、猜病模型工程、开源参考选择、LLM 运行架构，以及两条独立开发线的连接与合并策略
>
> 研究状态：本轮研究已结束；分层和共享层文档已经形成，具体实现、参数和产品空位仍需项目负责人审核

## 1. 原始问题与目标

项目希望同时推进两条工作线：

1. 游戏线：二维像素场景、角色移动、NPC、模拟经营、美术、音频、存档和浏览器体验；
2. 模型线：通过自由问诊、检查申请和诊断提交完成猜病玩法，并把它作为独立模型项目开发，在基础游戏完成后接入。

本轮需要回答：

- 现有 `docx/baseknowledge/` 内容分别属于游戏还是模型；
- 哪些开源项目应直接采用、哪些只借鉴、哪些应排除；
- LLM 的最小可行架构是什么；
- 两条开发线如何在早期互不阻塞；
- 最终合并 MVP 前需要哪一层共同接口；
- 如何把研究结论沉淀为项目文档和目录边界。

产品持续遵守以下约束：

- Web-first，桌面与移动浏览器为正式平台；
- 俯视 2D 像素风单人游戏；
- 医学教育与娱乐模拟，不用于真实患者诊断、治疗或急诊分流；
- 隐藏病例、答案、评分规则和模型密钥不进入客户端；
- 病例必须结构化、版本化并经医学审核；
- 游戏层和模型层前期可以分别独立完成闭环。

## 3. 外部来源核查

本轮实际查阅和交叉核对了以下官方项目或来源：

### 3.1 游戏技术

- [Phaser](https://github.com/phaserjs/phaser)：4.2.1、MIT；适合作为浏览器 2D 游戏运行时。
- [Phaser Next.js template](https://github.com/phaserjs/template-nextjs)：提供 React–Phaser bridge 思路；当前依赖仍以 Next 15.3.1、Phaser 4.0.0 为基线，不能直接作为本项目最终模板。
- [Tiled](https://github.com/mapeditor/tiled)：地图编辑器和 JSON 地图格式；编辑器许可证不自动改变用户导出地图和自制素材的许可证。
- [LibreSprite](https://github.com/LibreSprite/LibreSprite)：可作为开源像素编辑工具备选。
- [Aseprite FAQ](https://www.aseprite.org/faq/)：可以制作和销售素材，但编辑器使用受自身 EULA 约束。
- [`idb`](https://github.com/jakearchibald/idb)：IndexedDB 轻量 Promise 封装。

### 3.2 患者模拟和模型框架

- [PatientHub](https://github.com/Sahandfer/PatientHub)：MIT；角色、session、evaluate 和 profile adapter 值得借鉴，但其 Python/Burr/Hydra/Chainlit 运行时不宜直接成为当前 Next Web MVP 的底座。
- [EasyMED](https://github.com/FreedomIntelligence/EasyMED)：意图识别、患者模拟、轨迹评估很贴近本产品；README 声明 MIT，但 GitHub 主分支没有独立 LICENSE，当前只能参考职责拆分，不能默认复制代码、病例或量表。
- [AgentClinic](https://github.com/SamuelSchmidgall/AgentClinic)：代码 MIT；Patient、Measurement、Moderator 和检查工具协议值得参考；NEJM、MIMIC、MedQA 等案例的使用权不能由代码许可证推导。
- [EvoPatient](https://github.com/ZJUMAI/EvoPatient)：Apache-2.0；RAG、长期记忆、多专科和人格演化适合后续阶段，不进入 MVP。
- [MedAsk Benchmarks](https://github.com/medaks/medask-benchmarks)：MIT 评测代码；适合参考 OSCE 风格回归流程，vignette 来源仍需逐项核对。
- [MedSP1000](https://github.com/MAGIC-AI4Med/MedSP1000)：四角色病例包、冻结 rubric 和可恢复运行设计值得参考；仓库 LICENSE 的版权字段仍是占位符，上游 MedEdPORTAL 教学材料需要独立判断权利，不直接复用案例。
- [MedAgentSim](https://github.com/MAXNORM8650/MedAgentSim)：CC BY-NC-SA 4.0；可观察 Phaser 界面和模拟节奏，不进入商业产品代码或素材。

### 3.3 病例和术语

- [DDXPlus](https://github.com/mila-iqia/ddxplus)：Figshare 数据为 CC BY 4.0，适合离线生成症状、既往史、病种和鉴别诊断骨架；仍需中文化、难度筛选和医学审核。代码仓库未见许可证，因此不复制代码。
- [Synthea](https://github.com/synthetichealth/synthea)：Apache-2.0，适合生成纵向病程、就诊、药物、检验和 FHIR/CSV 数据；导出格式和术语仍要查 NOTICE。
- [Human Disease Ontology](https://github.com/DiseaseOntology/HumanDiseaseOntology)：CC0，可用于疾病 ID、分类和同义词参考。

## 4. 关键分析结论

### 4.1 不能只做游戏/模型二分

如果只有游戏层和模型层，会有一组概念没有稳定所有者：

- 患者 NPC 与病例会话的绑定；
- 检查设备与医学检查的映射；
- 问诊、检查、诊断和结果 API；
- 会话状态机；
- 流式事件和错误码；
- 病例客户端投影；
- 医学评分到游戏奖励的输入边界；
- 存档和服务端会话恢复；
- fixture、mock、契约测试和版本兼容。

因此采用三分法：

```text
game/  游戏层
model/ 模型层
share/ 共享连接层
```

### 4.2 游戏层所有权

游戏层拥有：

- 地图、移动、碰撞、遮挡、相机和场景切换；
- 玩家和普通 NPC 的表现与空间状态；
- React/DOM 问诊和结果 UI；
- 模拟经营、货币、设备、声望、任务和解锁；
- 美术、音频、资源加载和本地存档；
- 模型失败时的提示、重试和恢复体验；
- 对共享契约的游戏 adapter 和 mock 测试。

游戏层不拥有医学真相，不能读取答案和隐藏事实，也不能让模型直接改动经营状态。

### 4.3 模型层所有权

模型层拥有：

- 结构化病例、版本、发布和审核；
- Controller、Patient、Evaluator 的职责和 prompt；
- 事实披露、检查结果、答案和 rubric；
- 诊断同义词、疾病层级和评分；
- 安全、提示注入、真实病情输入处理；
- 模型评测、延迟、成本和审计事件；
- 对共享契约的模型 adapter 和 headless runner。

模型层不拥有地图、动画、游戏货币、库存、时间和解锁。

### 4.4 共享层所有权

共享层是双方唯一允许的直接连接面，拥有：

- 公共 DTO 和 JSON Schema；
- 稳定 ID；
- 会话状态机；
- HTTP API 与 SSE 事件；
- 错误、重试、幂等和恢复语义；
- 客户端允许看到的病例投影；
- fixture、mock 和 contract tests；
- 契约版本、兼容矩阵和合并门槛。

共享层不实现具体游戏玩法或模型推理。

## 5. 开源项目采用决策

### 5.1 直接采用

- Phaser 4.2.1：游戏运行时。
- Tiled 1.12.2：地图生产工具和 JSON 数据格式。
- IndexedDB + idb：本地存档。
- DDXPlus 数据：离线病例骨架，遵守 CC BY 署名。
- Synthea：离线纵向病程和检查数据生成。
- 许可证清晰的疾病术语本体：用于诊断归一化的参考数据。

### 5.2 借鉴但不整套引入

- Phaser Next.js template：借鉴唯一 Phaser 实例和 React bridge。
- PatientHub：借鉴角色隔离、会话记录、profile/evaluate 接口。
- EasyMED：借鉴意图—患者—评估职责拆分。
- AgentClinic：借鉴检查工具和 environment/measurement 协议。
- MedSP1000：借鉴角色包、冻结 rubric 和逐项评分证据。
- MedAsk：借鉴回归评测 harness。

### 5.3 延后或排除

- EvoPatient 的在线 RAG、长期记忆、多医生协作：延后。
- MedAgentSim：非商业许可证，不直接复用。
- MIMIC、NEJM、医院病历和来源不明医患对话：不进入公开产品。
- 通用向量数据库、Redis、任务队列和独立 FastAPI：没有明确需求前不引入。

## 6. 最小可行 LLM 架构

最终建议不是“多个自由 Agent 互相聊天”，而是“确定性状态机控制少数受限模型职责”。

```text
离线
DDXPlus / Synthea
  → Case Builder
  → 规则校验 + Critic
  → 医学人员审核
  → 版本化 CasePack

在线
玩家输入
  → 安全与越界检查
  → Controller LLM：严格 JSON action
  → 服务端确定性事实门控
      ├─ ask_patient → Patient LLM 口语化
      ├─ order_test  → 固定读取 CasePack
      └─ diagnosis   → 术语归一化和基础判定
  → Schema / fact-ID / state validator
  → 事件记录

结算
确定性覆盖分
  + Evaluator LLM 处理语义歧义和文字复盘
  → 带逐项证据的结构化评分
```

MVP 只有三个 LLM 职责：

1. Controller：分类动作，不生成病例事实；
2. Patient：只看 persona 和 allowed facts；
3. Evaluator：只在结束时看完整轨迹、答案和 rubric。

检查结果不是 LLM Agent。默认也不为每轮增加 Consistency LLM；先用 Schema、fact-ID 白名单、状态校验和失败重生成，只有高风险或抽样质检时再启用语义一致性模型。

## 7. 并行开发和合并策略

### 7.1 游戏线

游戏层使用 mock 模型，独立完成：

```text
探索 → 患者交互 → 问诊 → 检查 → 诊断 → 结果 → 奖励 → 存档
```

### 7.2 模型线

模型层使用 headless client，独立完成：

```text
创建会话 → 问诊 → 事实披露 → 检查 → 诊断 → 评分 → 轨迹导出
```

### 7.3 合并门槛

只有在以下条件全部满足后才进入统一 MVP：

- contract v1 冻结；
- 双方使用相同 fixture；
- 游戏 mock 闭环通过；
- 模型 headless 闭环通过；
- 状态、错误、幂等和断流恢复通过契约测试；
- 客户端构建和存储无隐藏病例、答案或 rubric；
- 病例和评分完成医学审核；
- 模型延迟、成本和安全达到待确定门槛。

## 9. 已决定、建议与未决定

### 9.1 已决定

- 前期采用 `game/`、`model/`、`share/` 三层。
- game 和 model 独立开发，不直接引用对方内部模块。
- share 是唯一共享连接面。
- 先各自通过 mock/headless 闭环，再合并 MVP。
- 隐藏病例、答案、rubric 和密钥留在服务端。
- 在线检查结果确定性读取病例包。
- LLM 不直接修改经营状态。

### 9.2 当前建议

- Next Route Handlers/BFF 承担 MVP 模型服务，明确需要后再拆 FastAPI。
- JSON Schema 作为语言中立合同，TypeScript/Pydantic 作为映射。
- Controller + Patient + Evaluator 三职责。
- Consistency LLM 不是每轮必选调用。
- DDXPlus + Synthea 只用于离线病例生产。

### 9.3 尚未决定

- 当前根目录 Next 壳迁入 `game/`，还是保留为最终集成壳；
- 模型层最终使用 TypeScript 还是 Python；
- 模型供应商、模型名称、预算和部署地区；
- 首批病种、病例审核人与审核流程；
- 评分到经验、金钱、声望和解锁的公式；
- 账号、每日挑战、排行榜是否进入首期；
- 服务端会话、日志和幂等记录的保留时间；
- 真实健康输入的正式提示、地区化急救信息和隐私策略；
- SSE 重连、单轮超时、单局调用次数和成本上限；
- 合并后继续保持三个 package，还是同一 Next 应用内逻辑分包。

这些项目已经在共享层文档中保留明确空位，等待审核填写。

## 10. 风险和后续工作

### 10.1 当前主要风险

- 游戏层模拟经营、美术素材和 NPC 行为的开源调研仍不充分；
- EasyMED、MedSP1000 等项目存在许可证或上游数据权利不完整的问题；
- Phaser 4 属于较新的主版本，仍需真实地图和移动端 PoC；
- 模型稳定性、延迟、成本和医学评分一致性尚无本地实测；
- 当前根目录工程还没有物理迁移成两个独立可运行项目；
- 共享契约目前是文档设计，还没有机器可执行的 Schema 和 contract tests。

### 10.2 推荐后续顺序

1. 项目负责人审核三份基线文档和共享层空位；
2. 冻结 `share` contract v1 的最小字段；
3. 决定根目录 Next 壳的迁移方式和模型层语言；
4. 创建机器可执行 Schema、fixture、mock server 和 headless client；
5. 游戏层完成代表性诊室与最小经营闭环；
6. 模型层完成 5 个审核病例的 headless 闭环；
7. 双方通过同一套契约测试；
8. 用一个病例完成真实集成，再扩展至 MVP 病例池。

## 12. 研究终止结论

本轮已经完成“如何划分项目、参考哪些开源内容、采用什么 LLM 架构、两条线如何独立开发以及如何合并”的研究目标。

当前最重要的成果不是选定某个多 Agent 框架，而是明确：

> 游戏层拥有世界和经营体验；模型层拥有医学事实和评分真相；共享层拥有双方共同遵守的接口、状态和版本。两边先独立闭环，再以契约测试为门槛合并 MVP。

后续工作已从研究阶段转为文档审核、契约落地和分线实现阶段。
